# ADR-003: 同期は OCC + コンフリクトコピー。「後勝ち」「先勝ち」を不採用

## ステータス

採択 (2026-04-29)

## コンテキスト

複数端末から同じファイルが同時に編集・上書きされたとき、サーバ側でどう解決するか。本システムの最重要設計判断。

## 検討した選択肢

### A. Last Write Wins（後勝ち）

最後の書き込みが採用される。実装は最も簡単。Dropbox の初期や多くの素朴なアプリで採用されている。

**致命的な欠点**：古い版で上書きされたとき、ユーザは「自分の変更が静かに消えた」ことに気づかない。これは本システムの最優先ゴール G-1（意図せぬファイル損失ゼロ）と直接矛盾する。

### B. First Write Wins（先勝ち）

先に書き込んだ方が採用される。後続は拒否される。

**欠点**：
- 「何が先か」の判定がサーバ時計依存
- 後続のアップロードが「ブロックされる」UX が混乱する
- アプリの中で "in-flight" 状態を扱う複雑さ

### C. OCC + コンフリクトコピー ← **採択**

クライアントは `If-Match: <known_version_id>` を送り、サーバは現在の version_id と一致するときだけ上書き。不一致なら HTTP 409 を返し、ユーザに「サーバ版を確認 / 別名で保存 / 強制上書き / キャンセル」を選ばせる。

**利点**：
- データロスが構造的に発生しない（自動上書きしない）
- 「衝突したことに気づかない」という最悪の事態を避けられる
- 不変条件 INV-3「自動マージ禁止」と整合

**欠点**：
- UI に選択モーダルを実装する必要がある（中コスト）
- ユーザに判断を委ねる UX なので、判断疲れが起きる可能性

### D. CRDT / 自動マージ

利点：意識せず動く

欠点：バイトレベルの自動マージは事故の元（バイナリファイルでは無意味、テキストでも複雑）。本システムはファイル全体の同期で、ブロック単位の編集を扱わないので過剰。

## 決定

**選択肢 C（OCC + コンフリクトコピー）** を採択する。

具体的には：

- アップロード時の必須ヘッダ：`If-None-Match: *`（新規）または `If-Match: <version_id>`（既存上書き）
- ヘッダなしのアップロードは HTTP 428 で拒否
- `If-Match` 不一致の場合は HTTP 409 + JSON 詳細を返し、HTMX が選択モーダルを描画
- ユーザが「強制上書き」を選んだ場合のみ `If-Match: *` で再送
- 「別名で保存」を選んだ場合のコンフリクトコピー命名規則：`<basename> (conflict YYYY-MM-DD HH-MM <device>).<ext>`
- 自動マージはサーバ・クライアントどちらでも行わない
