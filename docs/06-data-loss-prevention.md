# 06. ファイル損失防止戦略

> 「ファイルが意図せず失われる」という事象を、原因別に網羅し、各々に対する設計上の対抗策を定める。

## 1. 損失原因の MECE 分類

```
ファイル損失
├── A. ユーザ起因
│   ├── A-1. 誤操作（削除をクリック）
│   ├── A-2. 誤操作（上書きアップロード）
│   ├── A-3. 誤操作（フォルダごと削除）
│   ├── A-4. 認証情報紛失（パスワード忘れ・端末紛失）
│   └── A-5. ランサムウェア / 端末乗っ取りからの「全削除」
├── B. システム起因
│   ├── B-1. アプリケーションのバグ
│   ├── B-2. データベース不整合
│   ├── B-3. ストレージ層の物理障害
│   ├── B-4. アップロード途中の中断
│   └── B-5. デプロイ事故 (旧版にロールバックしたら DB スキーマと不整合)
├── C. インフラ起因
│   ├── C-1. AZ 障害
│   ├── C-2. リージョン障害
│   ├── C-3. アカウント侵害（AWS root 乗っ取り）
│   └── C-4. AWS 課金停止 (請求未払い等)
├── D. 外部脅威
│   ├── D-1. 攻撃者のデータ消去
│   ├── D-2. 公開リンク濫用
│   └── D-3. データ流出 (損失そのものではないが副作用として削除)
└── E. 規制・法務
    └── E-1. GDPR/個人情報保護法上の削除要求
```

## 2. 各原因への対策表

### A. ユーザ起因

| 原因 | 対策 | 設計上の節 |
|---|---|---|
| A-1 削除誤操作 | (1) 削除前確認モーダル (2) ソフト削除 30 日 (3) UI でゴミ箱が常時アクセス可能 | INV-1, INV-5, [`05`](./05-file-operations-logic-tree.md) §4 |
| A-2 上書き誤操作 | (1) OCC で版違いを検出 → 確認モーダル (2) 強制上書きしても旧版は S3 バージョニング保持 | INV-2, [`04`](./04-sync-semantics.md) §4 |
| A-3 フォルダごと削除 | (1) 影響件数を確認モーダルで表示 (>100 件で警告強化) (2) ソフト削除なので 30 日復元可 | [`05`](./05-file-operations-logic-tree.md) §4.1 |
| A-4 認証情報紛失 | (1) リカバリコード 10 個 (2) Email リセット | [`07`](./07-security.md) §3 |
| A-5 端末乗っ取り | (1) パスワード変更で全セッション失効 (2) アクティビティタイムラインで異常検知 (3) 30 日のソフト削除があるため、攻撃者が「ゴミ箱を空にする」までは復旧可 | INV-1, INV-5 |

### B. システム起因

| 原因 | 対策 | 設計上の節 |
|---|---|---|
| B-1 アプリバグ | (1) 不変条件を契約（`go test` で検証） (2) 構造化ログで原因追跡 (3) 監査ログから影響特定 | [`11`](./11-testing-strategy.md) |
| B-2 DB 不整合 | (1) RDS PITR (point-in-time recovery) 30 日 (2) 補正ジョブ（孤児検出） | [`02`](./02-architecture.md) §3.4, [`03`](./03-domain-model.md) §6.3 |
| B-3 ストレージ障害 | (1) S3 11 ナイン (2) S3 バケットバージョニング (3) S3 同一リージョン内の冗長配置 | [`02`](./02-architecture.md) §3.5 |
| B-4 アップロード中断 | (1) tmp 分離 + os.Rename 原子 (2) tus.io レジューム (3) SHA-256 検証 | [`04`](./04-sync-semantics.md) §6, INV-4 |
| B-5 デプロイ事故 | (1) スキーマは前方互換マイグレーション (2) ロールバック手順 (3) DB マイグレーションは backward-compatible に分割 | [`10`](./10-operations.md) §3 |

### C. インフラ起因

| 原因 | 対策 |
|---|---|
| C-1 AZ 障害 | RDS Multi-AZ、ECS Multi-AZ、S3 Files は AWS 管理 |
| C-2 リージョン障害 | v1 では受容（NG-6）。v2 で S3 クロスリージョンレプリケーション + バックアップリージョン候補 |
| C-3 AWS root 侵害 | (1) ハードウェア MFA を root に設定 (2) IAM ロール最小権限 (3) AWS CloudTrail 全リージョン有効 (4) 異常アクセスのアラート (5) S3 Object Lock の検討（v2） |
| C-4 課金停止 | (1) AWS 予算アラート (2) 自動引き落としを 2 つの支払手段で冗長化 (3) 月次でデータをローカル NAS にエクスポート（v2 候補） |

### D. 外部脅威

| 原因 | 対策 |
|---|---|
| D-1 攻撃者の消去 | (1) Argon2id + TOTP 2FA (2) ソフト削除 30 日 (3) 物理削除には UI 上のパスワード再入力 (4) 監査ログで異常検知 |
| D-2 公開リンク濫用 | (1) IP 単位レート制限 (2) アクセスログで濫用パターン検知 (3) 期限・パスワード設定の推奨 |
| D-3 データ流出 | (1) アプリ層 AES-GCM 暗号化 (2) S3 SSE (3) TLS 1.3 (4) CSP nonce |

### E. 規制・法務

| 原因 | 対策 |
|---|---|
| E-1 削除要求 | 個人専用なので、本人がオーナーなので問題なし。削除時は 30 日経たずに即時 purge する API（運用ツール）を用意 |

## 3. 多層防御モデル（Layered Defense）

```
┌─────────────────────────────────────────────────────────────────┐
│ L1: UI 確認モーダル (削除・上書き・公開リンク発行・ゴミ箱空)     │  ← 一次防衛線
├─────────────────────────────────────────────────────────────────┤
│ L2: アプリケーション層 OCC (If-Match)                            │
├─────────────────────────────────────────────────────────────────┤
│ L3: ソフト削除 30 日 (deleted_at)                                │
├─────────────────────────────────────────────────────────────────┤
│ L4: メタデータ層 file_versions (旧版チェーン)                    │
├─────────────────────────────────────────────────────────────────┤
│ L5: S3 バケットバージョニング (ストレージ層の旧版)               │
├─────────────────────────────────────────────────────────────────┤
│ L6: RDS 自動バックアップ + PITR (30 日)                          │  ← 最後の砦
├─────────────────────────────────────────────────────────────────┤
│ L7: 月次手動スナップショット (RDS + S3) → 別 AWS アカウント      │  ← v2 候補
└─────────────────────────────────────────────────────────────────┘
```

L1〜L5 が個別操作で常時稼働。L6 はインフラ事故。L7 は AWS アカウント侵害対応。

## 4. 「ファイルが消えた」と感じた時の復旧フロー

```
[ユーザ: 「ファイルが消えた」]
         │
         ▼
ステップ 1: アクティビティタイムラインを確認
         │
         ├── 'file.delete' があり 30 日以内
         │     → ゴミ箱から復元 (Restore button)
         │
         ├── 'file.purge' があり < 90 日
         │     → 運用 CLI で S3 旧版から復元 (10 操作)
         │
         ├── 'file.update' があり別端末から
         │     → バージョン履歴から旧版に巻き戻し
         │
         └── ログにない
               │
               ▼
         ステップ 2: 補正ジョブの結果を見る
               │
               ├── /_orphan/ にファイルがある
               │     → 運用 CLI で files テーブルに再登録
               │
               └── ない
                     │
                     ▼
               ステップ 3: RDS PITR で 30 日以内のスナップショットから復元
                     │
                     ▼
               ステップ 4: S3 バージョニングを直接調査
                     │
                     ▼
               ステップ 5: RDS 月次スナップショット (v2)
                     │
                     ▼
               「復旧不能」を初めて結論付ける
```

具体的な手順は [`10-operations.md`](./10-operations.md) §5。

## 5. 設計が「明示的に弱い」点と、その理由

完全な無敵設計を主張すると別の場所で破綻する。次の点は意図的に「弱い」ままにしている。

### 5.1 リージョン障害

- ap-northeast-1 全停止時、サービスは停止する
- v1 では「個人用なので数時間〜1 日の停止を許容」とする
- v2 で S3 クロスリージョン候補（コスト判断）

### 5.2 完全な物理破壊からの復旧

- 「90 日経過 + S3 ライフサイクルでの完全消去」より前のデータは S3 旧版から復旧可
- それ以降は復旧不能。これは設計上「無期限保持」の方が危険（ストレージコスト・コンプライアンス）と判断した結果

### 5.3 ストレージとメタデータの非同期境界

- §3.6 で述べた通り、S3 Files への書き込みと RDS への INSERT は **原子的ではない**
- そのため「ストレージにあるが DB にない」「DB にあるがストレージにない」状態が瞬間的に発生する
- 補正ジョブで掃除するが、その間にユーザがアクセスすると 500 が出る
- 受容範囲：1 日数件以下、自動復旧可能

## 6. 検証可能な保護指標

| 指標 | 目標 | 検証方法 |
|---|---|---|
| 30 日以内のソフト削除からの復元成功率 | 100% | E2E テスト（時計を進める） |
| 上書きで旧版が S3 上に残る割合 | 100% | 統合テスト |
| OCC で 409 が正しく返る割合 | 100% | 同期競合シナリオテスト |
| 補正ジョブの孤児検出から復旧までのリードタイム | < 24 時間 | 模擬障害テスト |
| RDS PITR で N 日前に復元できる割合 | N ≤ 30 で 100% | 月 1 回 DR リハーサル |

## 7. ファイル損失防止と性能のトレードオフ表

| 保護機能 | 性能影響 | 実装コスト |
|---|---|---|
| ソフト削除 (deleted_at) | ほぼなし (インデックスでフィルタ) | 低 |
| OCC 検査 | SELECT FOR UPDATE 1 回 | 低 |
| 二重 OCC (書き込み前後) | SELECT FOR UPDATE 2 回 | 低 |
| SHA-256 計算 | 1MB あたり数 ms | 低 |
| 書き込み後の検証読み取り | 書き込み量 × 2 の I/O | **中**: 大容量で性能ペナルティ |
| バージョニング | S3 ストレージコスト 1.x 倍 | 低 (S3 機能) |
| 監査ログ | INSERT 1 行 / 操作 | 低 |
| 補正ジョブ | バッチ実行のみ | 低 |

「書き込み後の検証読み取り」は大容量時にコスト増になるので、デフォルトは「ファイル末尾の認証タグ検証 + SHA-256 計算」のみで、検証読み取りは設定でオプトイン（v1 ではオフ、必要なら v2 でオン）。

## 8. 改ざん検出（Tampering Detection）

ファイル損失とは異なるが、関連するため触れる。

- アプリ層 AES-GCM の認証タグ（GMAC）が破損していたら復号失敗 → 500 + アラート
- SHA-256 を `files.sha256` に保存し、定期バッチ（月 1 回）で全ファイルを再計算 → 不一致で警告
- 改ざんされていたら、過去版から復元する手順がアクティビティタイムラインから明確

## 9. 「やってはいけない」パターン集

設計時に避けるべき具体的な実装パターン：

| パターン | 何が悪いか |
|---|---|
| `os.Remove` でいきなり物理削除 | INV-1 違反。ソフト削除を経ること |
| 「上書きで旧版が消える」実装 | INV-2 違反。常に file_versions に追加 |
| `If-Match` ヘッダなしのアップロードを許容 | OCC 機能が無意味化。428 で拒否 |
| 「自動でリネームして衝突回避」（SaveAsCopy を勝手に発動） | INV-5 違反。ユーザに選択させる |
| 監査ログを書く前にコミット | 監査の意義が崩れる。トランザクション内で INSERT |
| アップロード中の SQL ロックを長時間保持 | 他の操作が詰まる。最小区間に絞る |
| `SELECT current_version_id ... ` を `FOR UPDATE` なしで上書きチェック | レースコンディション。`FOR UPDATE` 必須 |
| `panic()` で握りつぶす | recover ミドルウェアで 500 + 構造化ログ |

これらは [`11-testing-strategy.md`](./11-testing-strategy.md) §6 で「アンチパターンテスト」として明示的に検証する。
