# ADR-004: 削除はゴミ箱 30 日 + S3 バージョニングの二段ガード

## ステータス

採択 (2026-04-29)

## コンテキスト

ファイル削除のセマンティクスをどう設計するか。即時物理削除は実装が単純だが、誤操作・攻撃・バグでの損失を構造的に防げない。

## 検討した選択肢

### A. 即時物理削除

DELETE で S3 オブジェクトを `os.Remove`、メタデータを `DELETE FROM files`。

欠点：誤操作 / 攻撃で復元不能。

### B. ソフト削除 + 即時物理削除の選択肢提供

ユーザに毎回「ゴミ箱に入れる / 完全削除する」を選ばせる。

欠点：UX が煩雑。「完全削除」を選ぶ習慣ができたら結局 A と同じ。

### C. ソフト削除 30 日 + バージョニング ← **採択**

「削除」は常にソフト削除（メタデータ `deleted_at`）。物理削除は次の AND で発火：
- ユーザの明示的な「ゴミ箱を空にする」操作
- 30 日経過（デイリーバッチ）

物理削除でも S3 バケットバージョニングで旧版は 90 日保持される（ライフサイクル）。

利点：
- 不変条件 INV-1（物理削除は二段階）と整合
- ユーザが間違えても 30 日以内なら確実に戻る
- ランサムウェア・侵入時の最後の防衛線として機能

欠点：
- ストレージコストが増える（とはいえ S3 は安い）
- 「すぐ消したい」ユースケース（プライバシー）に対しては「ゴミ箱を空にする」UI を別途用意

## 決定

**選択肢 C** を採択。具体的には：

- DELETE 操作はメタデータの `deleted_at` 更新のみ。S3 オブジェクトには手をつけない
- ゴミ箱 UI からの「個別物理削除」「ゴミ箱を空にする」は確認モーダル + パスワード再入力を要求
- 日次バッチ（ECS Scheduled Task）が `deleted_at < now() - 30 days` を物理削除キューへ
- 物理削除は `os.Remove` で S3 DeleteMarker 付与（バージョニング有効）
- S3 ライフサイクルポリシーが 90 日後に旧版を完全消去
