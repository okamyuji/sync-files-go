# 13. リスクと未解決事項（Risk Register）

> 設計時点で「解決していない」または「将来の検証が必要」な点を、隠さず明示する。

## 2. 受容済み（Accepted）リスク

明示的に「対策しない」と決めた事項：

| ID | 内容 | 理由 |
|---|---|---|
| A-01 | リージョン障害（ap-northeast-1 全停止） | v1 では受容。v2 で再検討 |
| A-02 | 完全な無停止デプロイ | Rolling Update での短時間 2 タスク並行を許容 |
| A-03 | ペネトレーションテストの外部委託 | コスト過大。v1 では gosec / govulncheck / OWASP ZAP 自動 |
| A-04 | OS ネイティブ自動同期クライアント | スコープ外（NG-1） |
| A-05 | クライアント側 E2E 暗号化 | スコープ外（NG-2）、v3 候補 |
| A-06 | 全文検索 | スコープ外（NG-8）、v3 候補 |
| A-07 | クロスリージョン DR | コスト過大、v2 候補 |

## 3. 未解決事項（Open Questions）

設計時に決めきれなかった点。実装に入る前に解消する：

### 3.1 NFS 上の `os.Rename` のアトミック性

- 同一 S3 Files マウント内のリネームは NFS v4.1+ の規定上アトミックなはずだが、AWS 実装の挙動を実機で検証する
- 検証項目：
  - クラッシュ中のリネーム → tmp / 確定 のどちらに残るか
  - 同名上書きリネーム時の挙動
  - 並行リネームの挙動

### 3.2 NFS 上の open 中ファイル削除

- ダウンロード中のファイルが他端末から削除されたとき、読み続けられるかを検証
- 検証コード：

```go
// 1 端末で open し読み続けながら、別端末で os.Remove
// 期待: 読み続けられる（POSIX 標準）
```

### 3.3 S3 Files の書き込みレイテンシ実測

- 設計目標 p95 < 5s（10MB アップロード）
- 実測して目標を達成するか、もしくは目標を見直す

### 3.4 Cloudflare Tunnel のスループット

- 大容量アップロード（500MB〜2GB）が想定速度で通るか
- Cloudflare Free プランのレート制限がないか

### 3.5 MySQL Read Replica の遅延実測

- 通常時の `Seconds_Behind_Source` をベースラインとして取得
- read-after-write window の最適値（3 秒？ 5 秒？）を実測で決定

### 3.6 アプリ層 AES-GCM のチャンク化方式

- 1 MiB チャンク + 連番 nonce 方式が標準的か、より良い方式があるか調査
- 候補：[chunked-AEAD-deterministic](https://github.com/google/tink) / NaCl SecretStream
- 標準ライブラリのみで実装する制約と整合するか

### 3.7 SSE の負荷

- 1 ユーザが 3 端末同時に開いたとき、SSE 接続が ECS タスクに与える負荷
- アイドルタイムアウトのハンドリング

### 3.8 法務的な点

- 公開リンクから誰かにファイルを渡す行為が法に触れるケース（児童ポルノ等の二次配布等）への対応
- 個人専用前提だが、利用規約を含めるべきか

### 3.9 ファイル名の互換性

- macOS の `.DS_Store`、Windows の `Thumbs.db`、改行コード混在ファイル名（CR / LF を含むファイル名）への対応
- 設計上は受け入れて中身は触らないが、UI でフィルタ表示するか

### 3.10 アクセシビリティ実機検証

- VoiceOver / NVDA / JAWS で操作可能か
- 個人用なので公式テストは不要だが、自分で検証する

## 4. リスクが顕在化したときの対応プロセス

```
[障害 / 兆候を検知]
   │
   ▼
[重大度の判定]
   ├── 致命的: データロス危機 → 即時対応
   ├── 高:     ユーザ影響大     → 1 時間以内に着手
   ├── 中:     ユーザ影響限定的 → 1 日以内に着手
   └── 低:     後で          → バックログ
   │
   ▼
[初動]
  - インシデントログを開く
  - 影響範囲特定
  - 暫定回避（feature flag / ロールバック / 縮退運転）
   │
   ▼
[根本原因分析]
  - 5 Whys / Postmortem テンプレート
  - 監査ログ / CloudWatch ログ / メトリクスを横断
   │
   ▼
[恒久対応]
  - 設計書（このディレクトリ）を更新
  - ADR を新規追加（必要なら）
  - テスト追加（同じ問題を再発させない）
```

## 5. テストできない / 想定外への備え

| 種類 | 備え |
|---|---|
| 0day 脆弱性 | govulncheck の常時稼働 + 監査ログ + 30 日ソフト削除 |
| AWS 自体の障害 | ステータス監視 + 多層防御 + DR 手順 |
| 自分の操作ミス | アクティビティタイムラインで巻き戻し可能 |
| ハードウェア破損（自分のクライアント PC） | サーバ側に常にコピーがある（同期の本質） |
| 自分の死亡 / 認知症 | 法務的な「デジタル遺品」議論。設計範囲外 |

## 6. 設計フェーズで未確認の重要な質問（実装前に必ず解消する）

- [ ] S3 Files が ECS Fargate 上で実際に NFS マウントできることを実機検証
- [ ] Cloudflare Tunnel が 2GB アップロードをエラーなく通せることを実機検証
- [ ] 30 日後のバッチ削除を時計操作テストで検証

- [ ] SSE が他端末への通知をきちんと届けること（ALB なし、Tunnel 経由）
