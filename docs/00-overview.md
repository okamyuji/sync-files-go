# 00. 概要

## 1. このシステムは何か

**個人専用のオンラインファイル同期サービス**。Web ブラウザから複数端末（PC・スマホ・タブレット）の間でファイルをアップロード・ダウンロード・整理し、サーバ側で「真実の唯一の場所」を保つ。Dropbox / Google Drive を「自分専用にもう一段シンプルに」した姿に近い。

技術スタック（要約）：
- **バックエンド**: Go（標準ライブラリ中心）+ HTMX 4.x
- **DB**: RDS for MySQL 8.0（Primary + Read Replica、`DBRouter` で読み書き分離）
- **ストレージ**: S3 Files（NFS マウント）+ S3 backend（バージョニング ON）
- **インフラ**: Docker + Terraform + ECR + ECS Fargate（arm64）
- **外部公開**: Cloudflare Tunnel（`cloudflared` サイドカー）+ サイドカー nginx（ALB は不採用）

## 2. プロダクトゴール

| 優先度 | ゴール | 達成の指標 |
|---|---|---|
| **G-1** | **意図せぬファイル損失の発生をゼロに近づける** | ユーザがファイル損失をクリティカル事象として報告するまでの平均期間を、設計上「無期限」に近づける（30 日 + バージョニングの保護期間内であれば必ず復元可） |
| G-2 | 複数端末からの編集で「黙って上書きされる」が起きない | 競合検出率 100%（OCC で `If-Match` を必須化）。自動マージは設計から排除 |
| G-3 | バックエンドは Go 標準ライブラリ中心、依存を最小化 | go.mod の direct dependencies が 10 個未満（DB ドライバ・S3 SDK 一部・テストライブラリ等は許容） |
| G-4 | UI は HTMX 中心で、SPA フレームワークを採用しない | JavaScript の総量が gzip 後 50KB 未満 |
| G-5 | Docker + Terraform で IaC 化し、ECR/ECS Fargate に再現性のあるデプロイ | `terraform apply` 1 回で環境構築が完了 |
| G-6 | 質素だがモダンな UI（タイポグラフィ・余白・コントラストに統一感） | 「テンプレ感のない」デザインを目指す（[`08-frontend-design.md`](./08-frontend-design.md) 参照） |

## 3. 非ゴール（v1 で実装しないこと）

明示的に **やらないこと** を書くのは設計の半分です。

| ID | 非ゴール | 理由 |
|---|---|---|
| NG-1 | OS ネイティブの自動同期クライアント（Dropbox デスクトップ版相当） | スコープ縮小。Web UI のみで完結させる（ヒアリング合意） |
| NG-2 | クライアント側 E2E 暗号化（ブラウザ内 WebCrypto） | HTMX 主体の UI と相性が悪く、サーバ側暗号化で十分と判断（[ADR-005](./adr/ADR-005-server-side-encryption-aes-gcm.md)） |
| NG-3 | リアルタイム双方向同期（CRDT・Yjs 等） | 「Web UI 手動同期」スコープでは過剰。SSE による「変更通知」までで止める |
| NG-4 | 共同編集（Google Docs 風） | スコープ外 |
| NG-5 | チーム機能・複数ユーザの権限管理 | 個人専用前提。ただしテーブル設計は将来の `org_id` 追加が容易になるよう余白を残す |
| NG-6 | クロスリージョンレプリケーション | コスト過大。v2 以降で再評価（[12-roadmap.md](./12-roadmap.md)） |
| NG-7 | Content-Defined Chunking（Rabin fingerprint・差分転送） | S3 Files は 1 オブジェクト=1 ファイルで自然に管理でき、CDC の主要メリットである帯域節約は v1 のスコープ（500GB/2GB 上限）では費用対効果が低い（[ADR-001](./adr/ADR-001-s3-files-vs-direct-s3.md)） |
| NG-8 | 全文検索（PDF / OCR / 画像中の文字） | 検索はファイル名 + タグのみ（v1）。全文検索は v3 候補 |

## 4. ユーザーストーリー（代表例）

### US-1: 単純アップロード

> ユーザは PC のブラウザで Web UI にログインし、`report.docx` をドラッグアンドドロップしてアップロードする。アップロード進捗が表示され、完了後にファイル一覧に表示される。

### US-2: 別端末から閲覧

> ユーザはスマホのブラウザで同じ Web UI にログインし、PC でアップロードした `report.docx` をダウンロードまたはプレビューする。

### US-3: 同名ファイルの上書き（OCC が成功）

> ユーザは編集後の `report.docx` を再アップロードする。クライアントは前回取得した `version_id` を `If-Match` で送り、サーバ側がそれと一致することを確認して新版を確定する。旧版は S3 バージョニングで残る。

### US-4: 同名ファイルの上書き（OCC が衝突）

> ユーザ A（PC）と ユーザ A（スマホ）が同じ旧版を持っており、両方が編集してアップロードする。最初の `If-Match` は通るが、2 番目は不一致で **HTTP 409** を返し、UI に「サーバ版が新しいです。どうしますか？」のモーダルを出す。**自動上書きは絶対に発生しない。**

### US-5: 削除と復元

> ユーザは間違えて `vacation.zip` を「削除」する。これはゴミ箱に入るだけで、即座の物理削除は発生しない。30 日以内に「復元」をクリックすれば元に戻る。30 日経過後、バックエンドのバッチが S3 上に DeleteMarker を付与し、S3 のライフサイクルがさらに 90 日後に完全消去する。

### US-6: 公開リンク

> ユーザは `slides.pdf` の右クリックメニューから「公開リンクを発行」を選ぶ。期限（最大 7 日）とパスワードを設定すると、HTTPS の URL が発行される。期限切れ／削除でリンクは即座に無効化される。

### US-7: 監査ログ

> ユーザは「最近の操作」ページを開くと、誰が（自分のみだが）・いつ・何を（アップロード／削除／公開／復元等）したかの時系列が見える。

## 5. ステークホルダー

| 役割 | 関心事 |
|---|---|
| 自分（オーナー兼ユーザー） | ファイル損失ゼロ・運用負荷低・コスト最小 |
| AWS（インフラ提供者） | 利用料 |
| 攻撃者（敵対的） | 認証突破・ファイル奪取・改ざん・ランサム |

攻撃者を「ステークホルダー」として明示するのは脅威モデリングのため（[`07-security.md`](./07-security.md) で詳細化）。

## 6. 全体スコープ図

```
┌──────────────────────── ユーザの世界 ────────────────────────┐
│  [PC]   [スマホ]   [タブレット]    すべてブラウザのみ          │
└──────────────────────────│─────────────────────────────────┘
                           │ HTTPS / TLS 1.3
                           ▼
                ┌──────────────────────┐
                │   Cloudflare Edge    │
                │   DNS / TLS / DDoS   │
                └──────────┬───────────┘
                           │ Cloudflare Tunnel (outbound only)
                           ▼
┌─────────────────────── AWS の世界 (ap-northeast-1) ───────────┐
│                                                                │
│   ECS Fargate Task: cloudflared → nginx → app (Go)             │
│                                  │                              │
│                   ┌──────────────┴──────────────────┐           │
│                   ▼                                 ▼           │
│           [RDS MySQL]                    [S3 Files (NFS)]       │
│           Primary (Write/RAW)            ファイル本体            │
│           Read Replica × 1               バージョニング ON      │
│           (binlog 経由で同期)             SSE-S3 既定            │
│                                                                │
│   [Secrets Manager]   [CloudWatch]   [VPC Endpoints]           │
└────────────────────────────────────────────────────────────────┘
```

詳細は [`02-architecture.md`](./02-architecture.md) を参照。ALB を不採用にした経緯は [ADR-007](./adr/ADR-007-cloudflare-tunnel-not-alb.md)、Primary を守る MySQL 設計は [ADR-008](./adr/ADR-008-mysql-read-replica-write-ahead.md)。

## 7. 用語集

| 用語 | 定義 |
|---|---|
| 同期 | サーバを介した片方向書き込みの累積。本システムでは双方向自動マージを含まない。 |
| 楽観的同時実行制御（OCC） | 事前にロックを取らず、書き込み時に「自分が知っているバージョンが今もそうか」を `If-Match` で検査する方式。失敗時は HTTP 409 |
| コンフリクトコピー | 競合検出時、片方を上書きせずに別名（例 `report (conflict 2026-04-29 device-A).docx`）で保存する方式 |
| ソフト削除 | メタデータに `deleted_at` を立てるだけで、ファイル本体（S3 上のオブジェクト）には手をつけない削除 |
| 物理削除 | S3 上のオブジェクトに DeleteMarker を付与（バージョニング有効時）または完全消去する操作 |
| バージョニング | 上書き時に旧版を保持する仕組み。本システムでは S3 バケットバージョニング + メタデータ上のバージョンチェーンの両方で管理 |
| ETag / version_id | サーバが各バージョンに付与する一意識別子。クライアントはこれを `If-Match` で送り、競合検出に使う |
| OCC ヘッダ | 本システムでは `If-Match: <version_id>` または `If-None-Match: *`（新規作成時） |
| アクティビティ | ユーザの操作（アップロード／ダウンロード／削除／公開／復元等）の時系列記録 |
| 公開リンク | 認証なしでファイルを閲覧／ダウンロードできる URL。期限・パスワード保護を設定可能 |
