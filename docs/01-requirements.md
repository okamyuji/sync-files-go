## 2. 機能要件（Functional Requirements）

### F-1. 認証・認可

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| F-1.1 | ユーザは Email + パスワードでサインアップできる | Email 確認なしでもログイン可能（個人専用のため）。ただしパスワード強度チェックあり |
| F-1.2 | パスワードは Argon2id で保存 | 設計書 [`07-security.md`](./07-security.md) §3.1 に従う |
| F-1.3 | 二要素認証として TOTP（RFC 6238）を必須化 | 設定後、ログイン時に TOTP コード入力を要求。バックアップコード 10 個発行 |
| F-1.4 | セッションは安全な Cookie + サーバ側セッションストア（MySQL Primary） | HttpOnly / Secure / SameSite=Lax。有効期限 7 日（再延長あり） |
| F-1.5 | パスワード変更時に全セッション失効 | サーバ側セッションテーブルから当該 user_id を一括削除 |
| F-1.6 | レート制限：ログイン失敗 5 回 / 15 分 でアカウントを 15 分ロック | IP ベースとアカウントベースの両方 |
| F-1.7 | 個人専用とはいえ、ロール概念を内部的に持つ（owner / public-link-viewer） | 公開リンクの閲覧者を `owner` と区別する目的。テーブル設計に反映 |

### F-2. ファイル操作

#### F-2.1 アップロード

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| F-2.1.1 | 単一ファイルアップロード（multipart/form-data） | 5MB 未満は単純アップロード |
| F-2.1.2 | 大容量ファイルアップロード（最大 2GB / ファイル） | 5MB 以上は **tus.io 互換のレジューム可能アップロード**（Tus-Resumable, Upload-Offset, Upload-Length, PATCH） |
| F-2.1.3 | アップロード進捗表示 | `htmx:xhr:progress` イベントから進捗バー描画 |
| F-2.1.4 | 同時アップロード上限 | UI 上は 5 並列まで（サーバ側はセマフォで 10 並列まで） |
| F-2.1.5 | ファイル名・パス検証 | NULL バイト・パストラバーサル禁止（[`07-security.md`](./07-security.md) §6） |
| F-2.1.6 | アップロード途中の中断・タイムアウトは正規パスに反映しない | INV-4 を実装。一時パス → 完了時にだけ `os.Rename` で原子的に確定 |
| F-2.1.7 | アップロード完了時にクライアントへ `version_id` を返す | 次回 OCC のため |

#### F-2.2 ダウンロード / プレビュー

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| F-2.2.1 | 認証済みユーザは自分のファイルをダウンロードできる | `Content-Disposition: attachment; filename="..."` |
| F-2.2.2 | ブラウザでプレビュー可能なファイル（画像・PDF・テキスト・動画）はインラインプレビュー | `Content-Disposition: inline`、Content-Type を厳格に MIME スニッフィング無効化（`X-Content-Type-Options: nosniff`） |
| F-2.2.3 | ダウンロードレート制限 | 1 ユーザあたり 100MB/s を上限（過大な帯域消費を防ぐ） |
| F-2.2.4 | 公開リンク経由のダウンロードは別 IP 単位レート制限 | 1 IP あたり 30 req/min |

#### F-2.3 上書き（同名再アップロード）

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| F-2.3.1 | クライアントは `If-Match: <version_id>` を送信する | 必須（送信なしは 428 Precondition Required） |
| F-2.3.2 | サーバは現在の `version_id` と比較する | 一致 → 上書き、不一致 → 409 Conflict |
| F-2.3.3 | 上書き成功時、旧版は S3 バージョニングで保持 | + メタデータ上の `file_versions` に新行追加 |
| F-2.3.4 | 409 時、UI に選択モーダルを出す | (i) サーバ版を見る (ii) 別名保存 (iii) 強制上書き (iv) キャンセル |

#### F-2.4 リネーム / 移動

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| F-2.4.1 | リネームはメタデータの `path` 更新のみで完了する（O(1)） | S3 上のオブジェクトキーは UUID で固定。`path` はメタデータ |
| F-2.4.2 | フォルダ移動も同上 | サブツリー全体の `path` プレフィックスを更新 |
| F-2.4.3 | 監査ログに記録、UI でアンドゥ可能 | アンドゥは 5 分以内（後述 F-8） |

#### F-2.5 削除（ソフト削除）

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| F-2.5.1 | DELETE 操作はソフト削除のみ | メタデータ上 `deleted_at = now()` を立てる。S3 オブジェクトは無傷 |
| F-2.5.2 | UI 上で確認モーダルを表示 | 「30 日以内なら復元できます」と明記 |
| F-2.5.3 | 削除フォルダは中身ごと再帰的にソフト削除 | が、各ファイルは個別に `deleted_at` を持ち、復元時に個別選択可 |

#### F-2.6 復元

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| F-2.6.1 | ゴミ箱画面から個別または一括復元できる | `deleted_at = NULL` に戻す |
| F-2.6.2 | 復元時、元のパスにすでに同名ファイルがある場合は別名復元 | コンフリクトコピー命名規則に従う |
| F-2.6.3 | 監査ログに記録 | |

#### F-2.7 物理削除（バッチ + 明示操作）

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| F-2.7.1 | デフォルトでは 30 日経過後にバッチが物理削除を実行 | バッチは 1 日 1 回（Cron）。ECS Scheduled Task または Lambda |
| F-2.7.2 | ユーザが「ゴミ箱を空にする」を実行すると即座に物理削除 | 確認モーダル必須（INV-5） |
| F-2.7.3 | 物理削除でも S3 バージョニングで完全には消えない | 90 日後にライフサイクルポリシーで完全消去 |
| F-2.7.4 | 物理削除は監査ログに「irreversible」フラグ付きで記録 | |

### F-3. 整理・検索

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| F-3.1 | フォルダ階層は最大 20 階層（深さ） | サーバ側で検証 |
| F-3.2 | フォルダ名・ファイル名は Unicode NFC 正規化して保存・比較 | macOS の NFD 問題回避 |
| F-3.3 | ファイル名の最大長は 255 文字（UTF-8 bytes ではなく Unicode 文字単位） | |
| F-3.4 | 1 ファイルに 0〜10 個のタグを付けられる | |
| F-3.5 | ファイル名・タグ検索は MySQL の FULLTEXT INDEX (parser=ngram) を使用 | 100ms 以内に応答（Read Replica で実行） |
| F-3.6 | 検索結果は最近順（更新日時 DESC） | |

### F-4. 共有：公開リンク

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| F-4.1 | 認証済みユーザは任意のファイルに対し公開リンクを発行できる | UUID v4 ベース URL |
| F-4.2 | 期限を設定できる（1 時間 / 1 日 / 7 日 / 期限なし） | サーバ側で `expires_at` を保存 |
| F-4.3 | パスワード保護を設定できる（Argon2id でハッシュ） | リンク先で別画面、入力後にダウンロード可 |
| F-4.4 | リンクは即座に無効化できる（取り消し） | `revoked_at` を立てる |
| F-4.5 | 元ファイルが削除されたら、公開リンクも自動的に無効化 | DB トリガー or アプリ側 |
| F-4.6 | アクセス履歴を保持（IP / User-Agent / 時刻） | 監査・濫用検出 |

### F-5. バージョン管理

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| F-5.1 | 各ファイルに対し過去版を最新から最大 100 版まで UI に表示 | 古い版は S3 上にも残るが UI からは見えない（取得 API はある） |
| F-5.2 | 任意の旧版を「復元（巻き戻し）」できる | 旧版の中身を新版として再書き込みする方式（旧版は残る） |
| F-5.3 | 旧版を個別に削除できる（ユーザ明示操作） | これも監査ログに記録 |
| F-5.4 | バージョン保持期間 | デフォルト無期限（ユーザが個別削除しない限り）。設定で「90 日」「1 年」を選べる |

### F-6. 競合解決（OCC）

詳細は [`04-sync-semantics.md`](./04-sync-semantics.md) 参照。

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| F-6.1 | 同一ファイルへの同時上書きを検出 | `If-Match` ヘッダ必須 |
| F-6.2 | 衝突時は 409 Conflict + JSON 詳細を返す | UI が選択モーダルを描画 |
| F-6.3 | コンフリクトコピー命名規則 | `<basename> (conflict YYYY-MM-DD HH-MM device-X).<ext>` |
| F-6.4 | 自動マージは行わない（INV-3） | |

### F-7. 通知（HTMX SSE）

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| F-7.1 | 別端末でアップロード／削除／更新があったら、SSE で「変更あり」バッジを表示 | ローカル UI を勝手に置き換えない |
| F-7.2 | バッジクリックで再読み込み | |
| F-7.3 | SSE 切断時は HTMX のリトライに任せる | バックオフあり（HTMX デフォルト） |

### F-8. 監査ログ / アクティビティタイムライン

| ID | 要件 | 受け入れ基準 |
|---|---|---|
| F-8.1 | すべての書き込み操作（作成・更新・削除・公開・復元）を `audit_log` テーブルに記録 | unix epoch + nano 精度 |
| F-8.2 | 「最近の操作」ページで時系列に表示 | 直近 1000 件、ページング対応 |
| F-8.3 | 一部操作（リネーム・移動）は 5 分以内ならアンドゥ可能 | 監査ログから直前操作を特定して逆操作 |
| F-8.4 | 監査ログは編集・削除不可 | INSERT のみ。RDS の権限分離 |

## 3. 非機能要件（Non-Functional Requirements）

### N-1. 信頼性 / データ耐久性

| ID | 要件 | 目標値 / 検証方法 |
|---|---|---|
| N-1.1 | ファイル本体の耐久性 | S3 の 11 ナイン（99.999999999%）に依拠 |
| N-1.2 | メタデータの耐久性 | RDS のマルチ AZ 配置（[`09-infrastructure-and-deployment.md`](./09-infrastructure-and-deployment.md)） |
| N-1.3 | 「意図せぬ削除」に対する保護 | INV-1 によりすべてゴミ箱経由 + バージョニング |
| N-1.4 | バックアップ | RDS は自動バックアップ 30 日保持 + 月 1 回手動スナップショット |
| N-1.5 | RPO（目標復旧時点） | 1 時間 |
| N-1.6 | RTO（目標復旧時間） | 4 時間 |

### N-2. 可用性

| ID | 要件 | 目標値 |
|---|---|---|
| N-2.1 | サービスの稼働率 | 99.9% / 月（個人専用なので過剰目標は置かない） |
| N-2.2 | メンテナンス時間 | 月 1 回、深夜 2 時間まで |
| N-2.3 | 計画外停止の通知 | ステータスページ（v2 候補。v1 は不要） |

### N-3. セキュリティ

| ID | 要件 |
|---|---|
| N-3.1 | TLS 1.3 を Cloudflare Edge で終端。Cloudflare ↔ cloudflared は QUIC ベースのトンネル暗号化 |
| N-3.2 | OWASP Top 10（A01〜A10）に対する対策実装（[`07-security.md`](./07-security.md)） |
| N-3.3 | 保存時暗号化：アプリ層 AES-256-GCM + S3 SSE の多重防御 |
| N-3.4 | 認証情報・暗号鍵は AWS Secrets Manager で管理、IAM で最小権限 |
| N-3.5 | CSP nonce 方式、HSTS / X-Content-Type-Options / Referrer-Policy 設定 |
| N-3.6 | 公開リンクは Bearer 風トークン（推測困難な UUID v4） |
| N-3.7 | DB パスワードは平文で持たず、Secrets Manager から起動時取得 |
| N-3.8 | コンテナイメージは Distroless / scratch ベースで最小化 |

### N-4. 性能

| ID | 要件 | 目標値 |
|---|---|---|
| N-4.1 | アクティブユーザ：自分一人 + 公開リンク経由のゲスト数名 | |
| N-4.2 | 単純ファイル一覧 API のレスポンス | p95 < 200ms（DB クエリ含む） |
| N-4.3 | アップロード（10MB） | p95 < 5 秒（VPS-S3 間の理論帯域に近い） |
| N-4.4 | ダウンロード（10MB） | p95 < 3 秒 |

| N-4.6 | UI 初回表示（Cold） | p75 < 2.5s（Web Vitals LCP） |

## 4. 制約（Constraints）

### C-1. 技術スタック

- バックエンド: Go 1.23+ 標準ライブラリ中心
- フロント: HTMX 4.x + Vanilla CSS（Tailwind 等の大型 CSS フレームワークは不採用）
- DB: MySQL 8.0.x on RDS（Primary Multi-AZ + Read Replica × 1）
- ストレージ: S3 Files（NFS v4.1+ マウント）
- 認証: 自前実装（Argon2id + TOTP）

### C-2. インフラ

- AWS リージョン: ap-northeast-1（東京）
- IaC: Terraform 1.7+
- コンテナ: Docker（Distroless ベースイメージ）
- レジストリ: ECR
- 実行: ECS Fargate

### C-3. 規模

- 単一テナント（個人）
- 総容量 500GB / ファイル上限 2GB（v1 デフォルト）
- 同時アクティブブラウザ 3 端末まで

### C-4. ライセンス

- MIT または Apache 2.0 を想定（v1 では未確定。コードは社外公開しない前提でも、依存ライブラリのライセンスは点検する）

## 5. 要件のトレーサビリティ

各要件は実装時に対応するテストと紐づける。詳細は [`11-testing-strategy.md`](./11-testing-strategy.md)。

| 要件 ID | 主な検証方法 |
|---|---|
| F-1.* | 認証統合テスト |
| F-2.* | E2E テスト（Playwright）+ 単体テスト |
